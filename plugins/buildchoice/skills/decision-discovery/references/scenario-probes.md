# 场景化候选发现探针（辅助，不是追问规则）

借鉴 Spec Kit 的需求覆盖检查与 GSD 的 gray areas：**先识别本轮功能可能出现的不同结果（正常、异常、重复、部分失败），再选相应的检查视角**。本文件仅帮助 `decision-discovery` 寻找功能取舍和实际后果，不是独立分类器、强制问题清单或事实来源；有风险不代表必须让用户选择。

## 使用顺序

1. 读取用户本轮原话、当前任务范围、已有确认、相关规格/代码。已明确的方案不再重新提问。
2. 先判断本轮是否是实施开发：纯解释、简单可逆样式修改和与用户决策无关的重构，正常继续。
3. 仅选择 **最多两种**与本轮直接相关的场景，可完全不选。每种场景只扫描会影响当前开发结果的事项；一个场景没有候选是正常结果。
4. 按「发现功能选择点 → 判断实际影响与用户归属 → 核对已有答案 → 判断当前依赖」筛选候选，并做反事实自检；真实证据先读，未读依赖进入 INSPECT。输出与 coverage 在**同一次提取**形成，不额外启动 LLM。
5. 没发现的决策不因 coverage 填写完毕就视作「检查完整」，不允许为了满足维度或场景的数量创造问题。

## 按开发行为选择探针

| 与当前开发直接相关的场景 | 只考虑与本轮有关的关键差异 | 不必因此询问的工程细节 |
|---|---|---|
| 用户信息、账户、共享、登录 | 内容由谁可见；账号丢失如何恢复；是否暴露给外部服务；权限变化是否影响已有用户 | 使用哪种路由库、内部令牌变量名 |
| 创建、修改、导入或删除数据 | 保存前需否确认；重复导入和覆盖/合并；错误记录是否跳过；部分失败是否保留结果；误删能否恢复；重要字段识别失败怎么办 | 合理事务、幂等、输入校验、一般序列化方法 |
| AI 识别、生成或自动执行 | 错误结果如何呈现或核对；是否自动执行不可逆动作；重复执行会否产生额外结果；是否向第三方发送资料；使用付费服务的预算限制 | 模型提示词的微调、可安全实施的内部重试和错误处理 |
| 支付、订阅、费用、通知 | 什么条件产生真实费用；扣款/提醒时机；重复事件是否二次计费；停止订阅的后果 | SDK 包装方式、UI 按钮间距 |
| 发布、导出、同步与外部集成 | 发布范围；是否自动覆盖线上内容；冲突处理；导出内容的隐私边界；服务不可用时的用户可见行为 | 环境变量名称、普通 HTTP 客户端库 |
| 旧项目迁移与功能范围变更 | 旧数据或旧客户端是否保留；有无不可逆切换；已有产品承诺是否改变；哪些能力属于本轮交付 | 可回滚的内部重构、命名和目录整理 |

场景没有命中时仍依照通用五类与分层判断流程，不因为不在表中而忽略重要的功能后果。

## 工程取舍视角（按当前任务选择，不逐项追问）

| 方向 | 需要查明的实际产品后果 | 常见无需交给用户的工作 |
|---|---|---|
| 数据完整性与一致性 | 覆盖、重复保存、多人编辑冲突是否丢失记录 | 合理事务、幂等和输入校验 |
| 备份与恢复 | 清除站点数据、设备损坏、故障后能否恢复 | 已有策略下的常规备份实现 |
| 性能与响应 | 实际数据增长后等待是否超出用户可接受范围 | 无明显代价的查询与索引优化 |
| 可扩展性 | 单人原型是否即将支持多人同时使用 | 不影响承诺的内部结构调整 |
| 可靠性与可用性 | 断网或服务异常时关键功能是否可用 | 合理超时与可恢复重试 |
| 技术依赖与锁定 | 更换服务时能否导出数据，迁移代价如何 | 普通客户端封装 |
| 兼容性与迁移 | 旧记录、旧客户端、不同设备能否继续使用 | 明确兼容约定下的代码调整 |
| 部署与回滚 | 更新失败是否能恢复正常服务与数据 | 已明确流程下的发布操作 |
| 资源与费用 | 服务器、存储或 API 是否带来显著持续费用 | 合理缓存与无业务代价的优化 |
| 安全与权限 | 是否出现敏感泄露、越权或接口暴露 | 常规安全实践不替代重大权限选择 |
| 长期维护 | 当前捷径是否阻碍已计划的重要功能 | 函数组织、命名和普通重构 |

每次只选择直接相关的视角，结合真实代码和计划，说明「触发条件 → 失败/代价 → 功能结果 → 可恢复性和工程缓解 → 是否需要用户取舍」。例如重复导入可以由已有幂等要求解决；覆盖还是合并若改变用户数据且无约定，则可能成为候选。技术本身的理论风险不够成卡；“采用什么数据库”通常不够具体，“是否需要多人同时编辑且保留全部修改”才对应用户关心的功能差异。MCP 仅补充有界的字面信号检查，不能证明运行时后果或评估所有工程风险。

## 一个完整例子

本轮需求：「给记账应用加入 AI 小票识别」；项目文件已有约定「所有记录保存到本地，只有用户确认后才正式入账」。

- 先读项目约定，标注「入账确认」为 resolved，**不应再问确认还是自动保存**。
- 如果实现即将把小票照片发送第三方而用户未授权，核实目前使用的服务和实际传输路径，再评估是否产生需用户确认的隐私选择。
- 如果本轮不会做云同步或真实支付，不因为场景探针中出现这些词就生成远期候选。
- 如果用户只是要求把按钮颜色改浅，全部场景可以不选、候选为空。

## 可选实验的验收条件说明

仅当用户明确请求 BuildChoice 实验验证、需要转换验收条件时，检查：

- 该条件是否从**当前选中的选项**直接推出？请在 `basis` 中说明原句/选择依据。不要补造新产品能力；无法推出的应回到原决策对话。
- 有什么**具体反例**会违反该条件？测试须真实区分正确实现与至少一个合理错误实现；不能仅检查某个变量等于自己设定的常量。
- 有无外部资料、真正独立于实现代码的预设用例或人工复核？若没有，应承认「Agent 自行推导条件并编写测试」的剩余偏差风险。
- 缺测试、只读代码、输入范围之外的服务与设备不得标为通过；保持 `inconclusive` 或说明范围。

这些实验条件说明只在用户明确请求 BuildChoice 实验验证时适用，不纳入默认开发流程；测试及解释使用 Codex 原生能力，不追加用户授权或提供独立需求认证。

## 用户可见的完成摘要

默认按 Codex 原生开发流程汇报改动和实际测试，不强制生成 BuildChoice 验证摘要。需要说明决策时可简述：

- **你决定了什么**：只复述已确认的选择；未确认必须标明。
- **落实情况**：正常测试如实说明命令、结果和范围，无需 BuildChoice current_pass。只有明确运行实验时，才用 current_pass 判断该实验历史结果是否仍有效；静态关联或失效结果不能冒充通过。
- **尚待处理什么**：存在待确认项、测试未覆盖部分或需复核文件时点出一项最相关的。

不展示内部 ID、MCP 调用名、账本原始 JSON 和多余长报表，除非用户主动要求。
