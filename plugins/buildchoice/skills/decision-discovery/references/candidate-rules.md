# 候选与程序校验的边界

**先检查当前拟议实现依赖哪些未确认的重要假设，再决定是否产生用户问题。** 不把“需求开放”“有多个设计方案”或风险标签本身当作追问理由。此方法嵌入现有候选发现，**不新增规划阶段、文件、工具调用、批准卡或固定提问数量**；无需探索的明确小改动直接继续。

## 从当前方案寻找关键假设（P0）

1. **确定任务及已有依据**：先结合本轮要求、实际项目、有效决定和适用约束，理解交付范围及主要用户目标。项目当前实现只能说明现状，不能反过来证明用户曾选择它。能查到的事实先查。
2. **仅构造当前步骤需要的最小拟议方案**：在现有推理中说清本轮打算交付什么、用户会怎样完成主要操作、可能发生什么关键数据/权限/费用后果。标出其中“Agent 准备自行采用，但用户没有明确指定”的假设；不要生成全面 PRD、全部页面或所有功能清单。
3. **对开放式任务做一次有意义的方案对照**：如果当前拟议范围仍有实质分歧，考虑**一个**同样符合已知目标、但会改变交付范围、核心操作或重要后果的合理替代方向。例如“可点击演示原型”与“持续保存真实记录的工具”。对比的是用户实际会遇到什么差异，不是任意罗列样式偏好、技术栈或大量方案。目标与范围已有充分依据时跳过对照。
4. **只提取关键且当前相关的假设**：能明确写出「当前拟采用的行为 → 合理替代行为 → 对用户可观察的不同后果 → 现有依据是否解决 → 当前步骤是否依赖」时，才形成候选。若替换方案只改文案、视觉样式或普通工程实现，不构成重要产品选择；如果候选只是“可能影响用户体验”而无具体行为差异，丢弃。可逆默认行为能满足目标时优先自主实施。
5. **目标本身不足时先补最少信息**：例如只说“做个用户交互界面”且项目也没有用途，无法构造可信的主要用户目标时，先询问界面要帮助用户完成什么，不编造两个业务方案凑决策卡。这是任务含义澄清，不把假设伪称为已确认的用户决定。若用户明确授权自由设计演示，则在该范围内合理自主推进，不重复要求审批。

上述最小方案和假设筛选**只在本轮推理中使用**，不会自动写入 SQLite、生成规范、升级为历史记忆或声称用户认可。需要持久化的真实选择仍走原有 Hook / MCP 记录入口；用户允许 Agent 设计一部分，不等于授权超出该范围的数据传输、付费或发布操作。

## 重要性与询问时机

把筛出的假设沿现有四步判断，不引入另一套状态：

1. **实质不同**：至少两种合理方案会改变交付范围、核心用户路径、重要信息披露、数据/权限/费用规则或明显的用户结果。
2. **用户决策归属**：明确选错的后果与返工范围；普通质量修复、无关界面说明、低代价可逆的设计默认值由 Agent 处理，不把能力不足转嫁给用户。
3. **依据是否解决**：检查真实用户要求、有效历史决定、适用项目约束以及用户明确允许自主发挥的范围；证据不足但可读取先 INSPECT，不凭当前代码自证需求。
4. **当前依赖与可逆性**：目前必须决定、无合理低代价可逆默认方案且影响重要产品行为才 ASK_NOW；独立步骤可继续则 DEFER；已有有效答案、委托范围内的合理默认或普通实现细节则 PROCEED。不要为补齐候选数而提问。

### 例：用户只说“做一个记账交互界面”

- 先看项目是否已定义交付形式。若没有，Agent 拟议“可点击演示原型”，并对照“能够长期保存和编辑真实账目的工具”；两者会改变数据保存与主要功能范围，这是**范围级候选**。
- 如果马上需要确定数据与页面结构，且选错意味着重做核心路径，可问“这次要可交互原型还是实际可用的记账工具？”；如果目前只构建可复用的静态布局，则 DEFER。
- 如果用户已经明确“只做可点击原型，用模拟数据，自由设计”，无需再次确认范围；导航、卡片风格、一般文案由 Agent 决定。
- Agent 擅自把“设计理念”“实现思路”放进最终页面，是界面内容生成/检查问题，不应据此询问用户是否想展示技术说明。
- 若 Agent 打算新增云同步或外部上传，必须结合实际本轮范围与授权重新判断，不能把“界面由你设计”当作数据处理授权。

## 从语义判断到提交

可被问出的假设沿用当前 Candidate/ScreenRequest 契约：用 question / impact / options 呈现**实际产品行为差异**，按现有 category（如 scope）和 suggested_action 提交；来源只引用实际读过、可核验的事实。没有可辩护的备选行为就不制造候选；仅缺少目标时直接做最小澄清，不捏造有两项选项的卡片。不要在新请求中增加“假设评分”或未经 Schema 声明的字段。

例如用户要识别后保存小票，但没有约定错误识别是否直接入账：先判断“核对后保存”和“自动保存”是否会产生重要不同后果、是否已有答案，以及当前是否必须确定。若用户已明确“核对后保存”，就不再提问；若当前只做识别，可暂缓保存取舍。

本仓库的[正反例](examples.jsonl)使用 semantic-choice-example.v1，包括开放范围、已委托、已解决、可暂缓、目标不足与普通 UI 内容等 P0 场景；它们是发现行为的示例，不是 MCP 输入或语义准确率证明。实际请求按[结构化内容](decision-content.md)和当前工具 Schema 生成。

## 风险与可选覆盖说明

风险说明用于解释取舍，不自动触发问题。engineering_risks 写在对应候选中；recoverability 只能为 easy / costly / irreversible / unknown，恢复办法写入 condition/consequence 等说明字段，不能用整句替代枚举。severity 为 low / medium / high，product_choice 为 yes / no / uncertain。

选项必须声明 risk_assessment；识别到具体风险时才附 risk_level、risk_warning、risk_basis=observed/potential、risk_reason、risk_condition 与 risk_evidence_refs，依据和触发条件遵守结构化内容规则。资料引用只证明文字存在，风险含义与是否现实由你判断。风险文案与评估状态不参与业务身份比较。敏感操作继续遵守宿主权限。

coverage 是同次提取的简短依据，维度为 data_storage / access_visibility / automation_confirmation / external_cost / failure_recovery / scope_delivery，最多六项，不必填满。每项 dimension/status/reason，status 为 resolved/candidate/not_applicable/uncertain，可附 evidence_refs/candidate_ids。覆盖记录不证明没有遗漏。

history_matches 可带真实 memory_id/revision、same/related/conflict/different_scope 和 rationale。相似不等于同一选择；只有范围、标识和规则状态核对可用、且你明确请求沿用时才复用。
