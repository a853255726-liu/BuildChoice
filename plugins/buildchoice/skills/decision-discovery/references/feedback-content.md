# 开发后用户最需要看到的反馈

<!-- buildchoice-guidance:completion:start -->
维护版本：`intent-alignment.v1`。

先理解用户要完成的事，再判断实际交付是否支持这一目标。功能通过和清单齐全只是证据；内容、操作、结果、范围或强调程度也可能产生实质偏差。说明对用户目标的具体影响。

分清用户要求、有效决定、项目约束、当前实现和 AI 解释。按真实对象、条件和范围解释约束；项目现状不能自证原始意图，原话真实也不保证解释正确。

核对实际项目、任务、交付版本与检查范围。代码阅读、结构检查、实际测试和画面观察各按真实依据表达；不补造基线、执行记录、认可或全面正确性。

先整体理解，再只对会影响目标的重要疑点深入；复用仍有效的证据。合理选择无需制造问题，允许没有发现。重要疑点已处理或具体列为待查时结束，不强迫类别配额、固定轮次或新增审阅角色。

先说明实际使用表现与重要差异；只有影响判断的具体缺口才写操作／画面、用户影响、下一步及处理者，能自行补查的先补。用户可直接说希望哪个操作怎样变化。详细证据按需查看，不用命令或测试数代替反馈，也不追加例行免责声明。

产品体验审阅且宿主支持时，先按[独立上下文审阅](independent-review.md)提交事实材料和交付物，保存实际首轮及按需复核，再组织用户反馈。区分产品目标、数据约束、运行约束和执行解释，项目当前说明不能自证原始意图。

## 接续已完成工作

先按[产品流程的完成后分支](product-review.md#已完成工作先定位对象)定位真实项目、任务和交付版本，选择原比较或当前检查；不重新取得事前认可。内容标准由本文件维护，原生卡和 message 展示见[对话呈现](conversation.md)。

## 按问题选择检查工具

先明确要核对的操作或画面，再从当前可用工具中选择足以回答它的检查组合。已有与当前版本一致的结果可以复用；仅在相关改动、失败或未解决问题需要时扩展检查，不要求每次遍历工具或完成整套验收。

声称完成或修复前，核对结论对应的真实证据及其来源、版本和覆盖范围：修改文件或子任务自报完成不能代替验证；修复应覆盖原失败路径。当前仍有效的结果无需为重复说明而重跑。这吸收了 verification-before-completion 的证据原则，沿用现有反馈契约，不增加独立验证阶段；见[适配来源](upstream-sources.md)。

| 待核对的问题 | 可选方法 | 结论范围 |
| --- | --- | --- |
| 保存、取消、搜索、删除恢复等功能行为 | 代码检查、已有测试、接口调用或实际操作 | 说明检查覆盖的输入、状态和结果；读到测试代码不等于执行过测试。 |
| 文字裁切、控件越界、重叠和窗口缩放等布局结构 | 控件或 DOM 的位置和尺寸、字体测量、可访问性树、相关尺寸与状态的程序检查 | 可发现结构问题；控件边界正常不能代替实际画面的视觉判断。 |
| 颜色、字体实际渲染、对齐和整体观感 | 窗口或浏览器查看工具、截图、用户提供的实际画面或试用反馈 | 限定到实际看过的画面和条件，不从结构信息推断全部视觉效果。 |

按技术栈选已有能力，例如桌面框架的控件几何与文字测量、网页的 DOM 边界和计算样式。Tk 只是可用示例，不是插件依赖。窗口尺寸、长文字、错误提示等仅检查与当前问题相关的状态；使用合成数据并沿用项目的数据范围约束。

工具超时或不可用时，遵循该工具的恢复规则做有限重试，再考虑能回答同一问题的替代方法。结构检查已经回答的部分保留结论，不因截图失败将整项反馈阻塞，也不默认要求用户补截图。仍未解决且影响使用判断的部分，才按下节说明具体情况、影响和下一步处理者。

保留实际执行结果、检查条件及对应行为，按现有 evidence/display 契约填写证据等级。代码阅读、几何测量、测试执行和画面观察不能互相冒充；没有宿主执行观察编号的报告文件仍按现有契约处理，不补造回调或提升检查标签。

## 四项用户可见内容

1. **这次主要改变了什么**：只用具体操作和结果建立整体认识。缺少旧记录时说当前怎样使用，不编造前后变化。
2. **优先值得你看的地方**：先讲重要偏差、未明确约定的行为和用户后果；没有发现就简短说明。原要求、实际行为、检查程度分开。具体行为的检查标签不能提升成全面验证。
3. **还有什么具体情况需要确认**：只列影响当前使用或判断的真实缺口，每项有操作/画面、影响、下一步和处理者。能自行补查的先补查；仍缺条件就说明下一步由谁处理。没有重要缺口就完全省略本节。不因每条行为仅查过代码就重复“证据不足、未经过运行验证、不能证明全部正确”；详细限制保留在 limits/evidence。
4. **如何表达修改意见**：用户直接说哪个操作应该怎样变化；你定位具体 finding，再说明理解和处理方式。只有重要取舍仍不明确时发原生问题卡，不要求所有功能重新认可。

保留真实的不确定性，但把它写成具体情况，例如“还需补看实际窗口的中文显示和排版；功能操作已测试”。只在确实做过相应测试时使用后半句。不要为了填模板编造缺口、风险、测试或下一步已经执行的结果。

## 结构化提交

新 create/supplement 提交 report={version:"behavior-feedback.v1", overview:[已提交的 finding_id]}，overview 最多五项；finding.summary 用一句话说实际表现，最多180字符。每项 display 有 title（最多48字符）、check（observed/tested/read/not_checked）；重要差异/额外/无法对照项还需 impact（最多160字符）。

check 来自真实当前依据：observed 对应可用操作记录，tested 对应真实测试返回，read 表示查到代码或文件，not_checked 表示尚无这类依据。测试/运行的 tested_behaviors 必须覆盖该 finding 的具体行为；缺少真实执行回调的报告文件不能声称 tested/observed。标签不证明语义判断正确。

只有重要、具体且会影响当前判断的缺口才填 display.gap={situation,effect,next_step,owner}，分别最多80/80/100字符，owner=agent/user。不要只填“尚未验证”或“进一步验证”。重要且完全未检查的 unknown 行为必须明确缺口，不能用省略字段把它藏起来。低影响、例行的限制留在详情中，不出现在第三节。

例：

```json
{"title":"窗口文字显示","check":"read","impact":"中文标签需要完整可读。","gap":{"situation":"窗口的中文显示和排版还没查看","effect":"暂不能判断文字是否完整显示。","next_step":"打开实际窗口检查中文标签和按钮排版。","owner":"agent"}}
```

正式审阅仍关联原 scenario/behavior_ids，不能覆盖原约定。补充检查没有新冻结场景：非额外项要对照时提交 reference={text,source}，来源按真实 user/decision/project 规则核验；未找到参照时判断为 unknown 或补充发现，变化来源保持 uncertain。supplement 的 tested_behaviors 使用该 finding_id 作为覆盖标识。项目资料只是参照内容，不自动变成用户认可。

程序会拒绝格式不合格、没有对应依据的检查标签、重要未检查项被隐藏、无效引用及假历史；内容错误返回字段级修正，证据原文不匹配返回 EVIDENCE_REPAIR_REQUIRED 的字段、路径和范围；其他来源或状态错误仍按具体异常处理。按错误修正后用新幂等键重试，不截断关键后果或另写一份绕过校验的报告。相关性、后果是否现实、语言是否清楚仍由你判断，程序不做关键词业务分类。

## 反馈后的处理

用户指出实现偏离已确认要求时 fix 并复查；希望改变原要求时走可信决定与新要求版本，再 change_requirement；没有原要求时先明确新要求，不把它冒充旧偏差。资料不足时 investigate，暂缓时 defer。反馈绑定真实当前用户消息与具体 finding，不能要求用户提供内部编号。修正后对照原基线或新的当前检查记录生成后续报告，关联 previous_review_id，保留历史。
